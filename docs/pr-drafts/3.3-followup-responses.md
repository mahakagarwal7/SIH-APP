## TL;DR

Adds mobile answers for reporter clarifications and routed supervisor checks. An additive backend RPC reports assignment freshness without exposing assignment rows hidden by RLS; stale checks stay read-only, while the existing web RPC remains unchanged.

## Behavior and scope

Requested clarification and independent verification previously stopped at an honest pending state on mobile. Roadmap 3.3 lets the report author answer the current structured question from My Reports and lets the routed independent verifier record assignment and work checks from My Work.

## Contract and decisions

- Calls existing `respond_clarification` and `decide_verification` functions plus the additive `verification_context_v2` read RPC through the authenticated Supabase client under production RLS.
- Uses direct business RPCs because the current Next.js routes require browser-cookie, same-origin sessions. This remains within approved delivery-plan decision D5; the companion API only adds a versioned read contract and preserves the existing web RPC.
- Re-reads report/question/claim or verification/revision/policy/membership context before enabling a response. The companion RPC compares assignment versions under server authority; each clarification is checked against its claim's immutable report-version snapshot, and stale verification stays visible and read-only.
- Preserves backend question types, permitted location choices, real calendar dates, explicit uncertainty and separate assignment/work attestations.
- Scopes reply drafts and command IDs to the active question, keeps an unsent draft visible in the original question's history after a stale refresh, and reuses a command ID only while that question's complete payload is unchanged, so questions cannot inherit hidden values and unknown-result retries remain idempotent.
- Pages complete follow-up histories with exact counts, sequences multiple open questions across separate claims, and caps individual location replies at eight choices while showing every server-offered option.
- Refreshes the changed follow-up and related report/review caches. Stale/failed writes retain entered text; successful writes clear it before the next question.
- Keeps cached screens read-only offline, skips focus refreshes while offline, and hides links to report drafts or withdrawn reports.
- States throughout the UI that replies and supervisor checks do not accept progress; the planner decision remains separate.
- Depends on [SIH122 companion PR #8](https://github.com/ShivenduShivu/SIH122/pull/8), whose additive migration introduces `verification_context_v2`; it preserves `verification_context` for current web clients and changes no tables or policies. No dependency, service-role secret or Alerts flow is added. See `docs/FOLLOWUP_RESPONSES.md` for the detailed contract.

## Manual device checks

Use only owner-designated production records; replies and attestations are durable audit events and a concrete clarification can queue new processing.

1. As a reporter, open Field → My reports and a submitted report with an open clarification. Confirm the original wording, claim state, validation flags and exact current question match the web report detail.
2. Answer each supported question type on designated records: permitted location, typed location, date, scope, assignment and detail. Confirm a response never appears as accepted progress.
3. Choose **Not sure** on a separate question. Confirm the planner sees the uncertain response and any new question/manual-review state.
4. Open the same question on web and mobile, answer it on web, then submit the preserved mobile draft. Confirm mobile reports a stale question, retains the draft and reloads current history.
5. As the routed supervisor, open Field → My work → Supervisor checks. Confirm another supervisor and the original reporter cannot see or decide that request.
6. Record assignment and work as confirmed with a reason. Confirm the manager queue returns the claim to pending review and the schedule remains unchanged.
7. On separate checks, record **Cannot confirm** and **Need details**. Confirm disputed/verification states and earlier reasons match the web follow-up panel. After **Need details**, confirm the form clears; a later deliberate check gets a new command ID.
8. Change the active revision, policy, assignment or verifier before submitting a prepared check. Confirm mobile rejects the stale response and preserves entered details.
9. Switch project, revoke membership and test offline. Confirm old checks disappear, writes remain disabled and no other project's cache is changed.
10. Interrupt connectivity immediately after either write, reconnect and retry without changing fields. Confirm exactly one response or decision exists.
