## Behavior and scope

Roadmap 0.2 replaces the foundation launch screen with email/password sign-in, session restore, an account view and device-local sign-out. Native sessions persist in SecureStore; loading, offline, expired-session, storage-error and missing-configuration states are explicit. Duplicate sign-in taps are ignored, passwords are cleared after attempts, and stale restore results cannot override a newer auth event.

The screen follows the Nirmaan book's page 8 masthead, navy/serif typography, thin rules and restrained forms. No feature screens or navigation choices are added.

This PR is stacked on `feature/0.1-project-foundation` ([PR #1](https://github.com/mahakagarwal7/SIH-APP/pull/1)), which remains unmerged. Its foundation is a review dependency; this auth diff is not independent of it.

## Contract and decisions

- Uses the existing Supabase password-auth contract: `signInWithPassword`, `getSession`, auth events, foreground token refresh and `signOut({ scope: 'local' })`. No database writes, new tables, RLS changes or web API changes.
- Uses the owner-selected production backend through ignored local configuration. `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` are the exact names. `app.config.ts` exposes only those public settings through Expo Constants; it rejects private-key formats without echoing values.
- Native storage is `expo-secure-store`, as required by the repository. Storage errors are surfaced with redacted messages; no plaintext persistence fallback. Browser preview sessions exist only in memory and disappear on reload.
- Refresh pauses while backgrounded/offline. Restored tokens must be unexpired to show an account. Auth state is not proof of project membership; future features must use existing server authorization.
- Uses SDK 2.117.1's default refresh coordination, following its [migration guidance](https://github.com/supabase/supabase-js/blob/master/packages/core/auth-js/migrations/lockless-coordination.md); no deprecated custom lock is configured. The controller separately prevents duplicate submissions and stale UI updates.
- Request timeouts prevent an unresponsive network from leaving the form waiting indefinitely. Restore additionally has a 15-second deadline. Local sign-out and unconfirmed server revocation are distinguished.
- Dependencies: Supabase SDK for existing auth, SecureStore for native session protection, Expo Network for connectivity state, URL polyfill for native SDK compatibility, and Node types for build-time config/tests. Root `app.config.ts` is required for Expo's public configuration.
- D5 business API transport, navigation, language/Alerts scope, voice recording and offline outbox decisions remain open. No automatic continuation to 0.3.

## Manual device checks

1. Fill the publishable/anon key in the ignored mobile `.env.local`, restart with `npx expo start --clear`, and sign in using an existing approved account. For exports after configuration changes, use `npm run bundle:check -- --clear`. Expect the account email, no project/role claims, and no password left in the form. Enter an incorrect password first and expect a readable error.
2. Close/reopen the app on Android and iOS. Expect restore of a valid session. Background/resume it and let a session refresh; confirm that expiry or revoked refresh credentials cannot retain a signed-in UI indefinitely. Check a real account with representative token size: mocked storage tests do not prove native size limits.
3. In airplane mode, restore an unexpired session; verify the offline banner. Once its token expires, expect sign-in, disabled until connected. Reconnect and retry. No report/outbox functionality exists in this slice.
4. Sign out online, then close/reopen; expect sign-in. Repeat offline; if remote revocation fails after local tokens are removed, expect the explicit server-confirmation message. Other devices must retain their sessions. Simulate a native storage deletion failure and verify that the UI does not falsely claim successful logout.
5. Check a locked/unavailable secure store and failed token write with a native test harness; expect a recoverable storage error and no newly signed-in account. Check OS backup/restore and reinstall behavior separately; keychain behavior is platform-specific.
6. Verify keyboard Next/Go, password masking/autofill, screen-reader labels, safe areas and large text on a physical phone. Confirm every control remains reachable in portrait and landscape.
7. In a browser preview, sign in and reload; expect sign-in again, with no persisted Supabase session in localStorage. Remove a public configuration value and restart Expo; expect the setup message without key/environment details.

## Remaining limitations

The local production URL is configured, but the publishable key is blank. Live production login, RLS, device SecureStore persistence, background behavior and physical-phone layout have not been verified. No APK or emulator build is claimed. Browser mocks and Metro exports are separate evidence from these checks.

SecureStore can reject values on a particular platform/device; such failures fail closed and remain visible. No password reset, sign-up, MFA, deep-link auth, project selection or feature data is included in 0.2.
