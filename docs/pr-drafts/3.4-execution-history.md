## Behavior and scope

Manager History was an unavailable placeholder even though production already exposes an authorized accepted-record contract. Roadmap 3.4 adds current completed-work context and a queryable accepted-evidence record with correction status, decision reasoning, reviewer/time, source identifiers, audit references and accepted facts. Search, discipline, evidence-status, selected-activity filters and 20-record paging match the supported web behavior. The layout follows design-book page 7.

## Contract and decisions

- Calls existing `execution_history(p_project)` and `schedule_snapshot(p_project)` functions through the authenticated Supabase client, then rechecks the selected `project_members` row.
- Uses the direct RLS-protected Supabase transport approved in `docs/DELIVERY_PLAN.md` D5. It adds no dependency, schema, policy, service-role secret or web-backend change.
- Rejects reporter/supervisor roles before history transport and rejects revoked, changed or cross-project context before exposing results.
- Validates at most 20,000 complete accepted rows, unique event/decision IDs, server ordering, duplicated evidence fields, strict import-provenance and media shapes, correction targets and effective/replaced status. The backend's prototype limit maps to a scoped-export instruction.
- Shows imported source sheet/row metadata and captured voice transcripts/photo captions with explicit fallback labels. A temporary network failure can show validated cached history as stale; denied access hides it.
- Uses accepted actual start/finish only for the completed-work section. Calendar date spans remain explicitly separate from working duration and productivity.
- Clears the project-scoped history cache and local filter/page state when the selected project changes.
- See `docs/EXECUTION_HISTORY.md` for the detailed contract and consistency boundary.

## Manual device checks

Use an owner-designated production planner/manager account whose selected project contains accepted and corrected test records.

1. Open Manager → History and compare the project, completed actual dates and accepted events with the same project's web History screen.
2. Search by activity ID, source ID, work area, evidence wording and decision reason. Filter each discipline, Current and Replaced, then clear filters.
3. Select a completed activity. Confirm only that activity's accepted evidence remains, then show all activities.
4. Expand audit details on a current and corrected event. Compare event, decision, audit, plan revision, correction target and facts with the web record.
5. Check an imported spreadsheet report and a mobile audio/photo report. Confirm source sheet/row, transcript, photo caption and missing-value labels match the original report.
6. Move across a history containing more than 20 matching events. Confirm newest-first order, stable range labels and no repeated/missing event.
7. Disable connectivity after loading History. Confirm cached records are labeled stale and refresh is disabled; repeat before any history is cached. Simulate a temporary server failure and confirm the cache is labeled stale.
8. Switch projects and confirm the prior project's records, filters, expanded audit and page do not appear.
9. Revoke or downgrade the membership, reconnect and refresh. Confirm history is unavailable and no accepted evidence remains visible.
10. Sign in as a reporter/supervisor and confirm Manager History does not expose accepted records.

## Remaining limitations

- Live production-RLS, cross-client, correction-chain and physical-device evidence remain pending designated accounts and records.
- The RPC returns the complete bounded history, so filtering and 20-record paging are local. Projects above 20,000 events require the later scoped export flow.
- Planner export remains roadmap 5.1. Read-only schedule, task hierarchy and manager overview remain separate planned PRs.
- Current schedule actuals and accepted history are separate stable reads rather than one database transaction; malformed or changed context is rejected, while a change immediately after the recheck can appear on the next refresh.
